# Паспорт проекта Scan Grader

За документ отвечает Артур (P1). Статус сдачи указан в [индексе пакета](../../README.md#контрольные-точки).

## 1. Пользователи и проблема

Scan Grader готовит черновик оценки рукописной работы по математике. Преподаватель создаёт предмет и публикует в нём задание с эталоном и максимальными баллами. Студент вступает в предмет по коду, чтобы открыть задание и загрузить готовый скан. Сервис сохраняет работу и предлагает балл с пояснением по каждой задаче. Преподаватель сверяет черновик со сканом, при необходимости исправляет оценку и утверждает итог.

Начнём с преподавателей и ассистентов вузовских курсов математики, которым студенты сдают рукописные работы в PDF. Выбор вуза остаётся рабочей гипотезой. Студенты этих групп тоже будут пользоваться сервисом.

Когда сканы поступают пачкой, преподаватель повторяет один и тот же процесс. Сначала нужно найти решение в PDF и сопоставить его с эталоном. Если в решении есть ошибка, её нужно объяснить, а затем записать балл. При проверке доказательства преподаватель также выясняет, обоснован ли каждый переход. Предполагаем, что короткий черновик по задачам ускорит работу, если большую часть предложений ИИ можно будет принять без правок.

Студенту важно находить задания в своём предмете и понимать, почему ему снизили балл. Преподавателю нужен список работ по заданию, чтобы открывать сканы и исправлять оценки перед публикацией. Эталон при этом должен оставаться закрытым для студентов.

## 2. Альтернативы и ценность

| Подход | Как проходит проверка | Компромисс |
| --- | --- | --- |
| Почта или мессенджер | Преподаватель получает файлы и проверяет их вручную. Когда работа проверена, он отправляет комментарий с баллом | Подходит любой формат, но результат приходится вручную связывать с файлом |
| Система управления обучением | Сервис группирует работы по заданию, а преподаватель вручную проверяет их и публикует оценки | Сдача и учёт уже организованы. Возможность получить черновик для рукописной математики зависит от системы |
| Ручная проверка с помощью ИИ | Преподаватель самостоятельно передаёт работу и эталон в инструмент проверки | Можно проверить пользу ИИ, но связывать ответ с конкретным студентом и заданием приходится вручную |
| Scan Grader | Студент находит задание в своём предмете и сдаёт PDF, после чего сервис готовит черновик. Преподаватель утверждает оценку в том же задании | Нужно подготовить эталон в `.tex`. Польза зависит от точности распознавания и времени, которое преподаватель тратит до утверждения |

Преподаватель получает **краткий черновик по каждой задаче** и может сразу сверить его с исходным PDF. После того как преподаватель утвердит оценку, студент увидит результат по своей работе.

## 3. Границы продукта

| В MVP | За пределами MVP |
| --- | --- |
| В Classroom преподаватель создаёт предмет и получает код. Студент регистрируется, указывает ФИО и группу в личном кабинете, а затем вступает по коду. В «Моих предметах» он видит свои предметы | Отдельное управление учебными группами и добавление сопреподавателей |
| Преподаватель публикует условия. Он загружает закрытый эталон в `.tex` с пронумерованными решениями и указывает максимум за каждую задачу | ИИ генерирует эталон либо сервис импортирует его из PDF или Word |
| Студент загружает готовый PDF и видит статус. Сервис сохраняет оригинал и при необходимости сжимает рабочую копию. ИИ читает страницы и сверяет решение с эталоном | Сканирование на сайте. Редактирование PDF с помощью рисунков или аннотаций |
| Сервис проверяет вычислительные задачи и развёрнутые доказательства. По номеру задачи можно найти предварительный балл с коротким комментарием | Проверка других дисциплин либо автоматическая публикация оценки |
| Преподаватель открывает исходный скан и при необходимости исправляет черновик. После утверждения студент видит свой итог | Массовый импорт и выгрузка оценок во внешнюю ведомость |

### Сквозные сценарии

1. **Сдача и предварительная проверка.** Преподаватель создаёт предмет, публикует в нём задание и сообщает студентам код предмета. Студент входит в аккаунт и вводит код. После вступления он выбирает задание в предмете и загружает PDF. Сервис сохраняет скан и показывает статус. Затем он связывает номера задач с эталоном. Преподаватель получает черновик либо узнаёт, почему работа требует ручной проверки.
2. **Утверждение результата.** Преподаватель открывает сдачу, чтобы сравнить замечания с PDF. Если нужно, он меняет балл и комментарий. Когда преподаватель утверждает итог, студент получает доступ к оценке по каждой задаче.

### Основные правила

- В MVP есть два типа аккаунтов. Преподаватель создаёт предметы, публикует задания и утверждает оценки. Студент вступает в предмет по коду, сдаёт PDF и видит свою оценку. При самостоятельной регистрации создаётся аккаунт студента. Для учебной демонстрации команда заранее готовит аккаунт преподавателя.
- Код выдаётся для предмета. Успешный ввод сохраняет участие студента, поэтому для следующих заданий в этом предмете код не нужен. Повторный ввод того же кода не создаёт вторую запись.
- Преподаватель публикует задания в своём предмете. Студент может открыть опубликованное задание и сдать PDF, только если вступил в этот предмет. Сервер проверяет участие и при прямом запросе.
- Задание можно опубликовать, если у каждой задачи есть эталонное решение и максимальный балл. Сервис фиксирует версию эталона при публикации и закрывает доступ к нему для студентов.
- Сервис связывает сдачу с заданием и ID студента. В MVP студент может сдать одну работу на задание. Если файл не прошёл проверку, студент может заменить его до принятия.
- Черновик показывает отдельную строку для каждого номера задачи. Балл должен находиться между нулём и максимумом. Если решение записано иначе или доказано другим корректным способом, само по себе это не снижает балл.
- Если фрагмент не читается или внешняя интеграция дала сбой, сервис сохраняет сдачу. Преподаватель может оценить работу вручную, а студент получает результат после утверждения.

## 4. Бизнес-требования

| ID | Цель | Заинтересованная сторона | Метрика | Исходное значение и цель |
| --- | --- | --- | --- | --- |
| BR-001 | Сократить время проверки | Преподаватель | Медианное активное время от открытия работы до выставления итоговых баллов | Базу измерим при ручной проверке. В пилоте проверим, сокращается ли время хотя бы на 20% при сопоставимой точности итоговых оценок |
| BR-002 | Привязать сдачу к заданию в нужном предмете и аккаунту студента | Студент и преподаватель | Доля валидных сдач, которые после вступления по коду привязаны к нужному заданию и аккаунту. Преподаватель должен видеть каждую такую сдачу | База неизвестна. Для приёмки должны пройти 100% из 20 валидных сдач |
| BR-003 | Дать преподавателю контроль над оценкой, чтобы студент получил понятный итог | Преподаватель и студент | Доля итогов, которые подтвердил преподаватель и в которых есть балл с кратким комментарием по каждой задаче | База неизвестна. Для приёмки требование должно выполняться в 100% из 20 утверждённых работ |

### Как проверим проблему и пользу

P1 проведёт от 3 до 5 коротких интервью с преподавателями и ассистентами. Разговор начнётся с недавнего задания. Попросим рассказать, как собирали сканы и сколько заняла проверка. Затем уточним, какие ошибки повторялись и где преподаватель хранил эталон. Чтобы понять, подходит ли формат `.tex`, попросим одного преподавателя подготовить пробное задание.

Для BR-001 соберём 20 обезличенных или специально подготовленных работ, в которых есть вычисления и доказательства. Преподаватель проверит сопоставимые поднаборы двумя способами. В одном случае он проверит работы вручную, в другом воспользуется черновиком сервиса. Если проверяющих несколько, будем чередовать порядок. Замерим активное время и отметим, какие предложения ИИ пришлось исправить. Итоговые баллы сравним с заранее подготовленной разметкой. Тестовые работы и результаты пилота пометим отдельно.

Для BR-002 и BR-003 используем воспроизводимые сценарии приёмки. Если H1 не подтвердится, пересмотрим ценность сервиса. Если не подтвердится H3, оценим, сколько работы потребует добавление второго формата после MVP.

## 5. Ограничения и риски

Компоненты сервиса и его данные находятся на одной учебной ВМ. На КТ-2 команда проверит образцы, выберет схему ИИ-проверки и зафиксирует требования к эталону и PDF. Перед выдачей файла сервер проверяет права пользователя в предмете, а для студенческого PDF также проверяет, кто сдал работу. Для тестовых обращений к внешним API используем обезличенные материалы.

| Риск | Вероятность / влияние | Владелец | Как снизим риск |
| --- | --- | --- | --- |
| При сжатии ухудшается распознавание формул или строк | Высокая / высокое | P3 | Сравним распознавание исходных и сжатых PDF на одном наборе. Если качество вызывает сомнения, преподаватель проверит работу по сохранённому оригиналу |
| Модель занижает оценку за корректное альтернативное доказательство | Средняя / высокое | P3 | Включим альтернативные доказательства в набор и оценим их отдельно от вычислений. Преподаватель сможет исправить результат перед утверждением |
| Преподавателю неудобно готовить `.tex` | Средняя / среднее | P1 | Подготовим короткий пример с номерами задач. На интервью проверим, помогает ли он создать задание |
| Прямой запрос раскрывает задание, чужой скан или эталон | Средняя / высокое | P2 | Сервер проверяет участие в предмете и право на конкретный файл. Проверим матрицу доступа, а запрос на ИИ-проверку сформируем без полей профиля |
| Внешний API ограничивает размер запроса, долго отвечает или дорожает | Средняя / высокое | P3 | Ограничим объём обработки и замерим расход на работу. При сбое сдача сохранится, поэтому преподаватель сможет повторить обработку или проверить работу вручную |
| ВМ перестаёт работать либо теряется файловый том | Низкая / высокое | P4 | Сохраним согласованные копии БД и файлов вне ВМ. Восстановление проверим на учебных данных |
