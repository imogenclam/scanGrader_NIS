# Паспорт проекта Scan Grader

За паспорт проекта отвечает Артур Галимов (P1). В версии КТ-2 преподаватель может исправить учебную оценку через API и опубликовать её для студента. [Проверенные критерии](../requirements/traceability.md)

## 1. Пользователи и проблема

Предполагаем, что сервис пригодится на вузовских курсах математики, где студенты сдают рукописные работы в PDF. В каждом скане преподаватель или ассистент ищет решение нужной задачи и сверяет его с эталоном. В доказательстве он проверяет, обоснован ли каждый переход. Если находит ошибку, её нужно объяснить, прежде чем выставить балл.

Студенту важно найти задание в своём предмете и понять, почему снижен балл. Преподавателю нужен список работ, из которого можно открыть исходный PDF и сверить его с черновиком ИИ по задачам. Если большинство предложений подойдёт без правок, проверка может занять меньше времени.

### Основания и гипотезы

| Тип | Основание | Что следует |
| --- | --- | --- |
| Требование | Регламент курсового проекта НИС, стр. 2, 4, 8–9 и 14 | Два сквозных сценария охватывают сдачу работы и публикацию результата. У каждой истории есть критерии приёмки, а для нефункциональных требований определены методы проверки |
| Решение команды | Согласованные границы Scan Grader | Вступив в предмет по коду, студенты сдают задания по математике в PDF. Преподаватель готовит эталон в `.tex` и утверждает итоговые баллы. Сервис рассчитан на одну учебную ВМ |
| Проектное решение | ИИ-проверка скана по эталону | В MVP ИИ должен предлагать балл по каждой задаче. На КТ-2 проверили, как система распознаёт два учебных выражения и передаёт текст с эталоном локальному оценщику. Рабочую модель выберем на размеченных работах |
| Гипотеза H1 | Интервью и замер времени | Ручная проверка серии сканов отнимает достаточно времени, чтобы преподавателю пригодился черновик ИИ |
| Гипотеза H2 | Приёмочный набор | Если скан читаем и эталон утверждён, ИИ может предложить балл с полезным комментарием и за вычисление, и за доказательство |
| Гипотеза H3 | Интервью и пробная настройка | Преподаватель готов оформить эталон одного задания в `.tex` с той же нумерацией, что и в условиях |

Интервью и пилот запланированы. Время ручной проверки и качество рекомендаций реальной модели ещё предстоит измерить. [Протокол опыта КТ-2](../quality/baseline.md#распознавание-скана)

## 2. Альтернативы и ценность

| Подход | Как проходит проверка | Компромисс |
| --- | --- | --- |
| Почта или мессенджер | Преподаватель проверяет файл вручную и отправляет балл с комментарием | Подходит любой формат, но результат приходится вручную связывать с файлом |
| Система управления обучением | Сервис собирает работы по заданию, а преподаватель вручную проверяет их и публикует оценки | Сдача и учёт уже организованы. Доступность черновика для рукописной математики зависит от системы |
| Ручная проверка с помощью ИИ | Преподаватель сам передаёт инструменту работу с эталоном | Можно оценить пользу ИИ, но ответ приходится вручную связывать со студентом и заданием |
| Scan Grader | В задании, куда студент сдал PDF, преподаватель сверяет краткий черновик по каждой задаче с оригиналом и утверждает баллы | Нужен эталон в `.tex`. Польза зависит от точности распознавания и времени до утверждения оценки |

## 3. Границы продукта

| В MVP | За пределами MVP |
| --- | --- |
| После регистрации студент указывает ФИО и группу в личном кабинете. В разделе Classroom «Мои предметы» он видит предметы, в которые вступил по коду | Управление учебными группами и добавление сопреподавателей |
| Чтобы опубликовать условия, преподаватель задаёт максимум по каждой задаче и прикладывает закрытый эталон в `.tex` с пронумерованными решениями | Генерация эталона с помощью ИИ или импорт из PDF либо Word |
| Студент видит статус загруженного PDF. Сервис хранит оригинал, а для распознавания при необходимости сжимает рабочую копию | Сканирование на сайте и редактирование PDF с помощью рисунков или аннотаций |
| ИИ сверяет вычисления и развёрнутые доказательства с эталоном. В черновике по каждому номеру задачи есть балл с коротким комментарием | Проверка других дисциплин или автоматическая публикация оценки |
| Преподаватель может исправить черновик по исходному скану. Студент получает утверждённый результат своей работы | Массовый импорт и выгрузка оценок во внешнюю ведомость |

### Сквозные сценарии

1. **Сдача и предварительная проверка.** Преподаватель создаёт предмет, в котором публикует задание, и передаёт студентам код. Студент входит в аккаунт, чтобы вступить по коду и сдать PDF по выбранному заданию. Сервис показывает статус сохранённой работы и сверяет решения с эталоном по номерам задач. Преподаватель получает черновик либо узнаёт, почему нужна ручная проверка.
2. **Утверждение результата.** Преподаватель сверяет замечания с PDF и при необходимости меняет балл и комментарий. Когда он утвердит итог, студент увидит оценку по каждой задаче.

### Основные правила

- При самостоятельной регистрации пользователь получает роль студента. Для демонстрации команда заранее готовит аккаунт преподавателя.
- Код достаточно ввести один раз для всего предмета. При повторном вводе запись об участии не дублируется.
- Преподаватель публикует задания в своём предмете. Открыть условия и сдать PDF может только участник, даже если он обращается к серверу напрямую.
- При публикации сервис фиксирует версию эталона и закрывает его от студентов. У каждой задачи должны быть эталонное решение и максимум баллов.
- Сдача связана с заданием и ID студента. Для этой пары сервис принимает одну работу, а отклонённый файл можно заменить до приёма.
- Балл в строке каждой задачи лежит в диапазоне от нуля до максимума. За иную запись верного решения или другой корректный способ доказательства снижать балл нельзя.
- Если фрагмент не читается или внешний сервис дал сбой, преподаватель может проверить сохранённую сдачу вручную.

## 4. Бизнес-требования

| ID | Цель | Заинтересованная сторона | Метрика | Исходное значение и цель |
| --- | --- | --- | --- | --- |
| BR-001 | Сократить время проверки | Преподаватель | Медианное активное время от открытия работы до выставления итоговых баллов | Исходное время измерим при ручной проверке. В пилоте ожидаем сокращения хотя бы на 20% при сопоставимой точности итоговых оценок |
| BR-002 | Связать сдачу с заданием в нужном предмете и аккаунтом студента | Студент и преподаватель | Доля корректных сдач, которые после вступления по коду видны преподавателю и связаны с нужным заданием и аккаунтом | Исходная доля неизвестна. На выборке из 20 корректных сдач требуется 100% |
| BR-003 | Сохранить за преподавателем контроль над оценкой и объяснить студенту его балл | Преподаватель и студент | Доля итогов с подтверждением преподавателя и баллом с кратким комментарием по каждой задаче | Исходная доля неизвестна. На выборке из 20 утверждённых работ требуется 100% |

### Как проверим проблему и пользу

P1 проведёт от 3 до 5 коротких интервью с преподавателями и ассистентами. На примере недавнего задания выяснит, как собирали сканы и сколько заняла проверка. Уточнит, какие ошибки повторялись и где хранился эталон. Одного преподавателя попросит подготовить пробное задание, чтобы проверить, подходит ли ему формат `.tex`.

Для BR-001 соберём 20 обезличенных или специально подготовленных работ с вычислениями и доказательствами. Разделим их на сопоставимые группы. Одну преподаватель проверит вручную, а для другой воспользуется черновиком. Если проверяющих несколько, порядок будем чередовать. Замерим активное время и отметим, какие предложения ИИ пришлось исправить. Баллы сверим с заранее подготовленной разметкой. Тестовые работы и результаты пилота пометим отдельно.

BR-002 и BR-003 проверим по воспроизводимым сценариям приёмки. Если H1 не подтвердится, пересмотрим ценность сервиса. Если не подтвердится H3, оценим, сколько усилий потребует второй формат эталона после MVP.

## 5. Ограничения и риски

На КТ-2 API работает в контейнере, а SQLite хранит данные на постоянном томе. Для MVP заданы лимиты размера и числа страниц PDF, а также бюджет внешних вызовов. На размеченных работах проверим, достигает ли действующая модель порога качества, и измерим время и затраты. Внешние API испытаем на обезличенных материалах. В MVP перед выдачей файла сервер должен проверить права в предмете, а для студенческого PDF также проверить автора сдачи. [Пороги и методы проверки](../requirements/nfr.md)

| Риск | Вероятность / влияние | Владелец | Как снизим риск |
| --- | --- | --- | --- |
| После сжатия формулы или строки распознаются хуже | Высокая / высокое | P3 | Сравним одни и те же PDF до и после сжатия. Если результат распознавания сомнителен, преподаватель сверится с оригиналом |
| Модель занижает балл за верное альтернативное доказательство | Средняя / высокое | P3 | Добавим такие доказательства в набор и оценим их отдельно от вычислений. Преподаватель сможет исправить балл до утверждения |
| Преподавателю неудобно готовить `.tex` | Средняя / среднее | P1 | На интервью дадим короткий пример с номерами задач и проверим, помогает ли он подготовить задание |
| Прямой запрос раскрывает задание, чужой скан или эталон | Средняя / высокое | P2 | Сервер проверяет участие и право на файл. Сверим ответы с матрицей доступа. В запрос к ИИ поля профиля не попадут |
| Внешний API ограничивает размер запроса, долго отвечает или дорожает | Средняя / высокое | P3 | Ограничим объём обработки и измерим расход на работу. При сбое сдача сохранится, чтобы преподаватель мог повторить обработку или проверить её вручную |
| ВМ перестаёт работать или теряется файловый том | Низкая / высокое | P4 | Согласованные копии БД и файлов сохраним вне ВМ, а восстановление проверим на учебных данных |
