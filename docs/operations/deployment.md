# План доставки и отката на учебной ВМ

Рабочий план команды Scan Grader от 24 ноября 2026 года. За процесс поставки в распределении ролей отвечает P4, за совместимость схемы данных отвечают оба участника. КТ-2 включает локальный запуск каркаса. Автоматическая доставка на ВМ запланирована на КТ-3.

## Среда

Целью служит одна Linux-ВМ с Docker Engine и Compose. Профиль S1 для испытаний предусматривает 2 vCPU и 4 ГБ памяти. Контейнер `app` работает от UID 10001. Порт `8080` внутри контейнера доступен на `127.0.0.1:${SG_PORT:-8080}` хоста. Для доступа с рабочего места к учебному стенду можно использовать SSH-туннель. Файл SQLite находится в томе `app-data` по пути `/data/scangrader.db`. Права на Docker и резервные копии ограничиваются администраторами стенда, поскольку в базе находятся учебные токены. Публичные сервисы ИИ в этом сценарии не вызываются. [Схема размещения](../architecture/d03-deployment.svg) · [Состав контейнера](../../Dockerfile) · [Compose](../../compose.yaml)

## Поставка

1. После успешного CI запланированный job КТ-3 публикует проверенный образ. Журнал поставки связывает commit SHA с неизменяемой ссылкой вида `registry/repository@sha256:…`. В нём сохраняются также digest предыдущего образа и версия схемы SQLite.
2. Перед обновлением администратор проверяет свободное место и совместимость схемы с предыдущей версией. Для согласованной копии записи приостанавливаются и контейнер останавливается. Копия всего тома, включая файлы WAL при их наличии, сохраняется в закрытом хранилище вне ВМ. После проверки копии можно продолжить обновление.
3. На ВМ job переходит в каталог версии с `compose.yaml`. Имя Compose-проекта постоянно, поэтому новая версия подключает тот же том. Переменные `RELEASE_IMAGE` и `PREVIOUS_IMAGE` содержат ссылки по digest из журнала. Функция для Bash ниже одинаково применяет обе версии.

```sh
apply_image() {
  docker pull "$1" || return 1
  printf 'services:\n  app:\n    image: "%s"\n' "$1" |
    docker compose -f compose.yaml -f - up --no-build -d --wait
}

apply_image "$RELEASE_IMAGE"
```

4. После готовности контейнера job вызывает `GET /healthz` и читает учебную сдачу с токеном её владельца. Проверка повторяется после отката. На действующем стенде команда только читает результат.

```sh
base="http://$(docker compose port app 8080)"
student=$(docker compose exec -T app scangrader token student)
curl -fsS "$base/healthz"
curl -fsS -H "Authorization: Bearer $student" "$base/api/submissions/1"
```

## Откат

Если новая версия не достигает готовности или не может прочитать контрольную сдачу, job фиксирует неудачу. При совместимой схеме выполняется `apply_image "$PREVIOUS_IMAGE"` с тем же томом. После чтения исходного статуса и оценки в журнал записываются digest возвращённого образа и результат проверки.

При несовместимой схеме работа с текущим томом останавливается. Его копия сохраняется для разбора. Предыдущая версия запускается с восстановленной предрелизной копией на другом томе. Перед переключением администратор сверяет версию схемы, число работ и контрольный результат. Окно возможной потери новых оценок фиксируется в журнале и согласуется до переключения. Цель DATA-01 для полного MVP составляет до 24 часов потери изменений и до 60 минут на восстановление. [Требования NFR-005 и NFR-007](../requirements/nfr.md)

## Проверка отказов

Если контейнер остаётся в состоянии `unhealthy`, команда `docker compose logs --tail=50 app` помогает обнаружить отказ при открытии БД или миграции. Следует сверить владельца тома, свободное место и поддержку версии схемы выбранным образом. При HTTP 409 для повторного утверждения преподаватель читает уже сохранённый итог через GET. Этот ответ относится к состоянию работы и сам по себе не служит основанием для отката. [Конфликт двух утверждений](../architecture/d06-failure.svg)
