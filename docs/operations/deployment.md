# План доставки и отката на учебной ВМ

План от 24 ноября 2026 года. За доставку отвечает Алина Лисянская (P4), а совместимость схемы данных проверяют оба участника. На КТ-2 сервис запускается локально. Автоматическая доставка на ВМ запланирована на КТ-3.

## Среда

Для стенда нужна одна Linux-ВМ с Docker Engine и Compose. Профиль S1 предусматривает 2 vCPU и 4 ГБ памяти. Контейнер `app` работает от UID 10001. Его порт `8080` доступен на хосте по адресу `127.0.0.1:${SG_PORT:-8080}`. С рабочего места можно подключиться через SSH-туннель.

База SQLite хранится на томе `app-data` по пути `/data/scangrader.db`. Она содержит учебные токены, поэтому доступ к Docker и резервным копиям есть только у администраторов. Стенд работает без публичных сервисов ИИ. [Схема размещения](../architecture/d03-deployment.svg) · [Состав контейнера](../../Dockerfile) · [Compose](../../compose.yaml)

## Поставка

1. После успешного CI скрипт доставки публикует образ. В журнале он связывает SHA коммита с неизменяемой ссылкой вида `registry/repository@sha256:…`, а для отката записывает контрольную сумму предыдущего образа (digest) и версию схемы SQLite.
2. Администратор проверяет свободное место и совместимость схемы с предыдущей версией. Для согласованной копии он приостанавливает запись и останавливает контейнер. Затем копирует весь том, включая имеющиеся файлы WAL, в закрытое хранилище вне ВМ. Проверив копию, продолжает обновление.
3. На ВМ скрипт переходит в каталог версии с `compose.yaml` и сохраняет имя Compose-проекта, чтобы подключить прежний том. Одна функция Bash принимает `RELEASE_IMAGE` при поставке и `PREVIOUS_IMAGE` при откате. Обе ссылки содержат digest из журнала.

```sh
apply_image() {
  docker pull "$1" || return 1
  printf 'services:\n  app:\n    image: "%s"\n' "$1" |
    docker compose -f compose.yaml -f - up --no-build -d --wait
}

apply_image "$RELEASE_IMAGE"
```

4. Когда контейнер готов, скрипт вызывает `GET /healthz` и читает учебную работу с токеном владельца. На действующем стенде проверка ограничена чтением. После отката скрипт повторяет оба запроса.

```sh
base="http://$(docker compose port app 8080)"
student=$(docker compose exec -T app scangrader token student)
curl -fsS "$base/healthz"
curl -fsS -H "Authorization: Bearer $student" "$base/api/submissions/1"
```

## Откат

Если новая версия не проходит проверку готовности или не читает контрольную работу, скрипт фиксирует сбой. При совместимой схеме он выполняет `apply_image "$PREVIOUS_IMAGE"` с тем же томом. Сверив исходный статус и оценку, записывает в журнал digest возвращённого образа и результат проверки.

При несовместимой схеме администратор останавливает работу с текущим томом и сохраняет его копию для разбора. На другом томе он восстанавливает копию, сделанную до обновления, и запускает с ней предыдущую версию. До переключения он сверяет версию схемы и число работ, а затем проверяет контрольный результат. Период возможной потери новых оценок нужно согласовать заранее и записать в журнал. Для полного MVP по DATA-01 допустима потеря изменений за период до 24 часов, а на восстановление отводится до 60 минут. [Требования NFR-005 и NFR-007](../requirements/nfr.md)

## Проверка отказов

Если контейнер остаётся в состоянии `unhealthy`, по журналу `docker compose logs --tail=50 app` проверьте, открылась ли база и прошла ли миграция. Сверьте владельца тома и проверьте свободное место. Убедитесь, что образ поддерживает версию схемы.

При HTTP 409 итог уже утверждён. Преподаватель может прочитать его через GET без отката сервиса. [Конфликт двух утверждений](../architecture/d06-failure.svg)
