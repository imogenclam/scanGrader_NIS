# Целевая среда и план доставки

КТ-2, редакция 1 от 22 ноября 2026 года. За запуск на учебной ВМ и GitHub Actions отвечает Алина Лисянская. Конфигурация локального запуска доступна в репозитории. Доставка на ВМ и испытание отката запланированы.

## Запуск и остановка

В профиле S1 предусмотрены Linux, Docker Engine с Compose 2.24 или новее, 2 vCPU и 4 ГБ RAM. Приложение принимает соединения на `127.0.0.1:8080` хоста. На стенде с удалённым доступом HTTPS-прокси завершает TLS, а `SG_SECURE_COOKIE=1` включает Secure-cookie. Том `classroom` содержит SQLite, закрытые файлы и локальную почту, если для стенда выбран этот режим. Внешняя доставка кодов требует настройки SMTP. [Настройки](../../.env.example) · [D-03](../architecture/d03-deployment.svg)

```sh
docker compose up -d --build
docker compose exec app scangrader -init-teacher
curl --fail http://127.0.0.1:8080/healthz
docker compose ps
```

При первом создании преподавателя команда выводит одноразово показываемый пароль. Текст `ok` и HTTP 200 означают, что процесс принимает запросы и видит БД. При 503 смотрят состояние тома и сообщения `docker compose logs --tail=80 app`. Команда `docker compose stop` останавливает процесс с сохранением тома, `docker compose start` поднимает прежний контейнер.

## Последовательность обновления и отката

1. После зелёного CI для конкретного SHA будущий job поставки публикует построенный образ и записывает его digest. Стенд получает именно этот digest. В журнале остаются SHA, новый и предыдущий digest, время и результат проверки.
2. На ВМ останавливается единственный процесс записи. Делается согласованная закрытая копия **всего** `/data`, включая файлы SQLite, PDF и эталоны. Копия хранится вне ВМ и связывается с предыдущей версией. Целевые RPO и RTO составляют 24 часа и 60 минут. БД открывает и мигрирует новый процесс.
3. После переключения проверяются `/healthz`, вход тестового преподавателя, чтение предмета и ранее принятого контрольного PDF. Доступ пользователей открывается после положительного результата этих проверок.
4. При сбое доставка получает статус `failed`. Новый процесс останавливается. Если прежняя версия понимает текущую схему, запускается прежний digest на существующем томе. Иначе копия до обновления восстанавливается на **отдельный том**, который подключается к прежнему digest. Том сбойной версии сохраняется для разбора.
5. После возврата проверяются здоровье, контрольные суммы PDF и эталона и утверждённая оценка. В журнал записываются время, digest и фактически восстановленная точка. При восстановлении из снимка могут потеряться записи, сделанные позже него. До открытия доступа в шаге 3 пользовательские записи во время переключения не принимаются.

Согласованность копии и длительность восстановления предстоит измерить в DATA-01. Фактические результаты после появления стенда вносятся в матрицу. [План качества](../quality/strategy.md) · [Матрица](../requirements/traceability.md)
