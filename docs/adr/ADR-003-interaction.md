# ADR-003. Синхронное утверждение результата через REST

Решение принято для локальной версии КТ-2 от 24 ноября 2026 года. За контракт оценивания отвечает Артур Галимов.

## Контекст

Для US-005 преподавателю нужен однозначный ответ на действие «Утвердить», а для US-006 студенту нужен опубликованный балл. Предварительная оценка может быть ошибочной. Поэтому полномочие публиковать итог принадлежит преподавателю. Требования к правам и независимой проверке правил заданы в NFR-003 и NFR-006. [Истории пользователей](../requirements/stories.md) · [Нефункциональные требования](../requirements/nfr.md)

## Выбор

Операция `POST /api/submissions/{id}/approve` принимает все оценки по работе в одном JSON-запросе. HTTP 200 означает, что транзакция завершилась. Если клиент потерял ответ, он может определить фактический результат через `GET /api/submissions/{id}`. Повторное допустимое утверждение получит HTTP 409. У студента отсутствует доступ к исходному черновику. В каркасе используются сгенерированные учебные Bearer-токены. [Контракт OpenAPI](../../api/openapi.yaml) · [Последовательность вызовов](../architecture/d05-review.svg)

| Другой вариант | Основание для отказа |
| --- | --- |
| gRPC между клиентом и сервисом | Типизированные сообщения полезны при нескольких внутренних клиентах. Для двух операций с учебной работой REST позволяет проверить контракт обычным HTTP-клиентом |
| Команда через очередь с ответом о приёме | Подтверждение приёма сообщения ещё не означает публикацию оценки. Понадобились бы состояние ожидания и проверка доставки даже для короткой транзакции на одной ВМ |

## Последствия и пересмотр

Черновик в демонстрации берётся из учебных данных. Отдельный опыт передаёт распознанную формулу и эталон тестовому оценщику. Решение о выборе рабочей модели зависит от измерений на размеченном наборе S2. Если утверждение потребует длительных внешних операций или появятся независимые потребители событий о публикации, команда пересмотрит способ обмена.
