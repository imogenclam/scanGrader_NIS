# ADR-001. Границы сервиса оценивания

Решение принято для локальной версии КТ-2 от 24 ноября 2026 года. Владельцы документа — Артур Галимов и Алина Лисянская.

## Контекст

По историям US-005 и US-006 преподаватель утверждает оценку, после чего студент получает результат. Обе операции должны одинаково определять владельца работы и её состояние. Команда разворачивает сервис на одной учебной ВМ. Для такого стенда важны изоляция данных по NFR-003 и воспроизводимый запуск по NFR-005. [Требования](../requirements/nfr.md)

## Выбор

Принят модульный монолит на Go. Пакет `api` разбирает HTTP-запрос и проверяет роль. Пакет `grading` определяет допустимые баллы и поля студенческого ответа. Пакет `storage` отбирает работу по владельцу и в транзакции сохраняет утверждённый итог. Один процесс использует эти правила для обоих участников. Распознавание скана пока исследуется отдельным локальным экспериментом. [Компоненты](../architecture/d02-components.svg) · [Точка входа](../../src/cmd/scangrader/main.go)

Команда рассмотрела два других варианта.

| Вариант | Основание для отказа |
| --- | --- |
| Отдельные сетевые сервисы прав и оценивания | Для одного перехода состояния потребовались бы два развёртывания и обработка частичного сетевого отказа. В текущем сценарии у этих компонентов один жизненный цикл |
| Приложение в браузере с локальной базой | Клиент студента получил бы контроль над хранимым состоянием. У двух участников не было бы общего доверенного источника итоговой оценки |

## Последствия и пересмотр

Каркас собирается в один образ и проверяется без внешней модели. При обновлении сервер и его прикладные правила поставляются вместе. Если обработка реальных сканов исчерпает ресурсы одного процесса и сорвёт целевое время ответа на S1, команда проверит выделение обработчика в отдельный процесс.
